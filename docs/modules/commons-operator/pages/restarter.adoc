= Restarter
:description: Automatically restart Pods or StatefulSets using Stackable Commons Operator based on expiration dates or stale configurations.

The Stackable Commons Operator can automatically restart Pod objects based on certain criteria.
This can be applied to either the Pod or certain controller objects (such as StatefulSet).

== Pod

Pods are evicted when any of their restart criteria (listed below) expire, with the expectation that their owning controller is then responsible for restarting them.

Because they are evicted rather than deleted, this process should respect PodDisruptionBudget constraints, allowing users to ensure that clusters are restarted gracefully.

=== Expiration date

Annotation:: `restarter.stackable.tech/expires-at.\{tag\}`

Pods can be configured to expire at a certain point in time.
In this case, the Pod should have the annotation `restarter.stackable.tech/expires-at.\{tag\}` set to a datetime formatted according to RFC 3339 (such as `"2022-04-21T13:24:15.225774724+00:00"`).
`\{tag\}` should be a deterministic but unique ID identifying the reason for the expiry.

Multiple `expires-at` annotations can be set on the same Pod, in which case the *earliest* expiration datetime takes precedence.

== StatefulSet

StatefulSets are rolling-restarted when any of their restart criteria (listed below) expire.

=== Stale configuration

Label:: `restarter.stackable.tech/enabled`

The operator can restart StatefulSets when any referenced configuration object (ConfigMap or Secret) changes.
To enable this, set the `restarter.stackable.tech/enabled` label on the StatefulSet to `true`.

Annotation:: `restarter.stackable.tech/ignore-configmap.*`
Annotation:: `restarter.stackable.tech/ignore-secret.*`

These annotations can be added if the restarter is enabled on a StatefulSet, but some ConfigMaps or Secrets should be excluded from triggering a restart. `*` can be replaced with any value and is only used to make the annotation key unique.

[source,yaml]
----
---
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: statefulset-with-enabled-restarter
  labels:
    restarter.stackable.tech/enabled: "true"
  annotations:
    restarter.stackable.tech/ignore-configmap.0: hot-reloaded-configmap
    restarter.stackable.tech/ignore-secret.0: hot-reloaded-secret
spec:
  template:
    spec:
      volumes:
        - name: configuration
          configMap:
            name: hot-reloaded-configmap
        - name: credentials
          secret:
            secretName: hot-reloaded-secret
...
----

Annotation:: `restarter.stackable.tech/change-tracking-mechanism`

This annotation selects what counts as a change of a referenced ConfigMap or Secret:

`resource-version` (default):: Every write to the object counts as a change, including writes that only touch its metadata (labels, annotations, managed fields) or that write identical content.
`data-hash`:: Only a change of the content (`data` and `binaryData` of a ConfigMap, `data` of a Secret) counts as a change.
Writes by third parties that leave the content as it is do not restart the Pods.
To hash the content, the operator reads a referenced object whenever its resource version changes.
It only keeps the hash, not the content.
The hash is keyed with a random key stored in a Secret in the operator namespace and bound to the UID of the object, so the hash in the Pod template annotations reveals nothing about the content beyond whether it equals an earlier content of the same object.
On the first use of `data-hash`, the operator creates this key in the Secret `commons-operator-restarter-digest-key` in its own namespace.
Deleting that Secret, or the namespace, makes the operator create a new key on its next start, which changes every hash and therefore rolling-restarts every StatefulSet using `data-hash` once.

With any other value, the operator logs an error and stops updating the Pod template annotations of the StatefulSet until the value is fixed.
Switching from `data-hash` to `resource-version` changes the values of the Pod template annotations described below and therefore rolling-restarts the StatefulSet once.
Switching from `resource-version` to `data-hash` does not restart the Pods by itself: the operator keeps the value of every referenced object that has not been written since the Pods were last rolled.
The next write to such an object restarts the Pods once, as it would have with `resource-version`, and from then on only content changes do.

[source,yaml]
----
---
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: statefulset-with-content-based-restarts
  labels:
    restarter.stackable.tech/enabled: "true"
  annotations:
    restarter.stackable.tech/change-tracking-mechanism: data-hash
...
----

==== Pod template annotations

To detect changes, the operator adds an annotation for every referenced ConfigMap and Secret to the Pod template of the StatefulSet.
Its key is `configmap.restarter.stackable.tech/\{name\}` or `secret.restarter.stackable.tech/\{name\}`, its value is the UID of the referenced object, followed by its resource version or, with the `data-hash` mechanism, a hash of its content.
The value is `changes-ignored` instead if the object is excluded, either by the StatefulSet annotations described above or by the `restarter.stackable.tech/ignore` label described below.
The value is also `changes-ignored` if the referenced object does not exist (yet), for example because the StatefulSet was created before a mounted Secret.
This is intended: once the object is created, the value changes as described above (unless it is excluded), and the Pods are restarted to pick it up.
Kubernetes rolling-restarts the Pods whenever one of these values changes.
These annotations are managed by the operator, there is no need to set them yourself.

Object names can be up to 253 characters long, but Kubernetes limits the part of an annotation key after the `/` to 63 characters.
Longer names are therefore truncated and filled up with the hash of the original name to make sure there are no clashes.

== ConfigMap/Secret

Label:: `restarter.stackable.tech/ignore`

If a ConfigMap or Secret is only used for initializing a StatefulSet or contains data which can be hot-reloaded, add the label `restarter.stackable.tech/ignore: "true"` to avoid unnecessary restarts of the StatefulSet Pods:

[source,yaml]
----
---
apiVersion: v1
kind: ConfigMap
metadata:
  name: hot-reloaded-configmap
  labels:
    restarter.stackable.tech/ignore: "true"
...
---
apiVersion: v1
kind: Secret
metadata:
  name: hot-reloaded-secret
  labels:
    restarter.stackable.tech/ignore: "true"
...
----

Unlike the StatefulSet annotations `restarter.stackable.tech/ignore-configmap.\*` and `restarter.stackable.tech/ignore-secret.*`, this label affects every StatefulSet that references the labeled ConfigMaps or Secrets.
